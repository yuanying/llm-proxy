# 0005. 鍵・token をログに出さず、アクセスログは決めた欄だけにする

- Date: 2026-10-30
- Status: Accepted

## Context

llm-proxy は、上流の token（access token と refresh token）、呼び手から届くアサーション、ログインの途中の認可のコードや PKCE の verifier を扱う。どれもログに出れば、ログを読める者がそれを使える。ログは集めて長く残されることが多く、扱いは token のファイルより緩い。

要求と応答の本文には、呼び手の会話がそのまま入っている。これもログに出す理由が無い。

## Decision

### アクセスログに書くもの

要求 1 つにつき、終わったときに 1 行の構造化ログ（JSON）を標準エラーに出す。欄は次のものだけである。

| 欄 | 中身 |
|---|---|
| method | 要求のメソッド |
| path | 要求のパス。クエリ文字列は書かない |
| status | 返した状態コード |
| duration | 要求を受けてから応答を書き終えるまでの時間 |
| subject | アサーションで確かめた主体。確かめる前に断ったときと、確かめない設定のときは空 |

ヘッダ、クエリ文字列、本文は書かない。断ったときの理由（ADR 0004 のどの段か）は、アサーションの中身を含めずに短い文で書く。

### 書かないもの

- access token、refresh token、アサーション、認可のコード、PKCE の verifier、state。
- 上流（API と OAuth）が返したエラーの本文。OAuth のエラーで書くのは状態コードと、JSON の `error` の値だけにする。成功した token の応答と同じ形の本文が、エラーの形で返らないとは言い切れないからである。
- 要求と応答の本文。

token を持つ値の型は、文字列にしたときもログに渡したときも、中身を伏せた形にしか出ない。うっかり型ごとログに渡しても漏れないようにするためである。テストでは、ログの出力に token の値が含まれないことを確かめる。

`llm-proxy login` は、人に認可の URL を見せるために端末に出す。認可の URL には state と PKCE の challenge が入るが、challenge は verifier のハッシュであり、verifier は出さない。token は端末にも出さず、書いたファイルの場所だけを出す。

## Consequences

ログからは、誰がいつどのパスを呼び、どうなったかが分かる。何を話したかは分からない。上流のエラーの中身を調べたいときは、呼び手の側で応答を見る（Proxy はエラーの本文をそのまま呼び手に返す。ADR 0001）。
