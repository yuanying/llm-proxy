# 0004. gated のアサーションを確かめて、直接の到達を断る

- Date: 2026-10-30
- Status: Accepted

## Context

llm-proxy は、届いた要求に本物の token を付けて上流へ送る。誰の要求でも通せば、届く者は誰でもサブスクリプションを使える。

想定する置き方では、Proxy の前に gated（Kubernetes の Ingress controller。ログインや ServiceAccount の token で呼び手を確かめ、許された主体の要求だけを転送する）が立つ。呼び手は自分の ServiceAccount の token を付けて gated を通り、gated が TokenReview でそれを確かめる。

しかし gated を通らずに Proxy へ届く道がある。

- クラスタの中の Pod から、Service や Pod の IP へ直接届く道。NetworkPolicy が効いていなければ、どの Pod からでも届く。
- gated の設定が fail-open になる道。認可の規則の参照を書き間違えれば、守ったつもりの入口が誰にでも開く。

どちらも Proxy の側では気付けない。Proxy が自分で「この要求は gated を通った、許された主体のものだ」と確かめられる必要がある。

gated は、主体が決まった要求をバックエンドへ転送するとき、`Gated-Assertion` ヘッダに署名した短い主張を付ける。JWS の compact 形式で、署名は Ed25519、発行元・主体・要求のホスト名・発行時刻・期限（60 秒）を持ち、公開鍵は中央認証ホストの `/__gated/jwks.json` で配られる。クライアントが付けた `Gated-` で始まるヘッダは、gated が転送の前に消す。ServiceAccount の token で通った要求の主体は `system:serviceaccount:<namespace>:<name>` になる。

## Decision

### 要求のたびにアサーションを確かめる

`serve` は、healthz を除くすべての要求で、転送の前にアサーションを確かめる。順番は gated が示すとおりである。

| 段 | 確かめること | 満たさないとき |
|---|---|---|
| 1 | `Gated-Assertion` がある | 401 |
| 2 | JWS の compact 形式で、`alg` が `EdDSA`、`typ` が `gated-assertion+jwt` | 401 |
| 3 | `kid` の公開鍵が、設定の JWKS にある | 401 |
| 4 | その鍵で署名が検証できる | 401 |
| 5 | `iss` が設定の発行元と一致する | 401 |
| 6 | `aud` が設定の自分のホスト名と一致する。要求の `Host` とは比べない | 401 |
| 7 | `exp` が過ぎておらず、`iat` が未来すぎない。時計のずれは 30 秒まで許す | 401 |
| 8 | `sub` が設定の許す主体の一覧にある | 403 |

受け付ける `alg` は自分の側で `EdDSA` に固定し、アサーションに書かれた値は信じない。JWKS の URL もアサーションからは読まず、設定から取る。

アサーションを確かめてから、パスとメソッドを確かめる（ADR 0001）。確かめられない者には、どのパスがあるかも見せない。

許す主体は gated の認可の規則と同じものを、もう一度ここに書く。二重に書くのは意図したものである。gated の設定が fail-open になったときも、この一覧が残って断る。

### 公開鍵はキャッシュする

JWKS は、最初の要求のときに取り、応答の `Cache-Control` の `max-age` か 5 分の短い方だけ使う。知らない `kid` のアサーションが来たら、前に取ってから 1 分以上経っていれば取り直す。取れなかったときは、キャッシュの鍵を使い続け、1 分は取り直さない。取りに行くのは同時に 1 つだけで、待ち時間は 10 秒である。

Ed25519 の署名と JWS の読み取りは Go の標準ライブラリで書く。アルゴリズムが 1 つに決まっているので、JOSE のライブラリを入れて得るものは少ない。

### 設定しなければ起動しない

アサーションの設定は、発行元・JWKS の URL（既定は発行元の `/__gated/jwks.json`）・自分のホスト名・許す主体の一覧の 4 つである。発行元を設定せずに起動すると、`serve` は起動を拒否する。

確かめずに動かすには、確かめないことを明示するフラグを付ける。手元での試験や、別の仕組みで守っている置き方のためである。付ければ、起動のときに警告をログに出す。確かめないことを既定にすると、設定を忘れた置き方が静かに誰にでも開く。

### 退けた案

**NetworkPolicy で、gated からの通信だけを許す。** Proxy の外の仕組みで、Proxy は何もしなくてよい。しかし効くかどうかはクラスタの CNI と運用の慣習に依り、Proxy からは確かめられない。gated の fail-open も防げない。置く側が足すのは自由であり、この決定と並べて使える。

**呼び手の ServiceAccount の token を Proxy が自分で TokenReview する。** gated が無くても使える。しかし gated は確かめた token を後ろへ渡さないので、gated の後ろでは使えない。Proxy に Kubernetes の client と TokenReview の権限が要り、要求のたびに API サーバへ問い合わせる。

**gated と Proxy の間の共有の秘密（ヘッダの固定値）。** 実装は簡単だが、gated は任意の固定ヘッダを付けない。秘密は長命で、主体とも結び付かない。

**相互 TLS。** gated は後ろへ平文の HTTP で話す。主体も伝わらない。

## Consequences

gated を通らずに届いた要求にはアサーションが無いので、401 で断られる。gated の設定を誤って誰にでも開いた場合も、ログインしていない者にはアサーションが付かず、ログインした者でも許す主体の一覧に無ければ 403 になる。

許す主体を、gated の側と Proxy の側の 2 か所に書く。片方だけを直すと、通れない方に倒れる。

gated の中央認証ホストが落ちていても、キャッシュの鍵で確かめ続ける。最初の JWKS を取れなければ、Proxy はすべての要求を断る。

アサーションは gated が要求のたびに作るので、healthz を除き、gated を通らない道（kubelet の probe など）からは何も通らない。healthz は何も返さず、token にも触れない。
