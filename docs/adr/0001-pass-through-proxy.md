# 0001. Responses API をそのまま通す Proxy にする

- Date: 2026-10-30
- Status: Accepted

## Context

ChatGPT のサブスクリプションには「Sign in with ChatGPT」という OAuth のログインがあり、そこで得た access token は、ふつうの API キーと同じように `Authorization: Bearer` に置いて OpenAI の Responses API（`https://api.openai.com/v1`）へ送れる。

同じアカウントを使うエージェントが複数あると、それぞれが自分でログインし、それぞれが token を持つことになる。refresh token は 1 回しか使えないので、token のファイルを写して共有すると、先に refresh した方だけが生き残り、もう片方は切れる。ログインを 1 か所にまとめ、token を 1 つのプロセスだけが持ち、呼び手にはそのプロセスを経由させたい。

呼び手の多くは、OpenAI の SDK で Responses API を直接話すエージェントである。そうしたクライアントは、思考の続き（暗号化された reasoning の項目）や prompt cache の鍵（`prompt_cache_key`、`session_id` などのヘッダ）を、要求の本文やヘッダに載せて送る。別の API（Chat Completions など）へ橋渡しする Proxy では、こうした欄が橋渡しの過程で落ちる。

## Decision

### 変えるのは資格情報だけ

llm-proxy は、受け取った要求を上流の Responses API へ転送し、応答をそのまま返す逆 Proxy とする。要求と応答の本文には触れない。読みもしない。

要求のヘッダで変えるのは次のものだけである。

| ヘッダ | 扱い | 理由 |
|---|---|---|
| `Authorization` | 本物の access token の Bearer に置き換える | 呼び手は本物の token を持たない。呼び手が付けたものは捨てる |
| `Cookie` | 捨てる | 呼び手のブラウザや中継の Cookie を上流へ渡さない |
| `Gated-` で始まるもの | 捨てる | 手前の認証（ADR 0004）が付けたアサーション。上流には意味が無く、期限内なら他へ持ち込める値である |
| `Forwarded`、`X-Forwarded-*`、`X-Real-IP` | 捨てる。自分でも付けない | 手前の Ingress が付けた、クラスタの中のアドレスである。上流に知らせる理由が無い |
| hop-by-hop のヘッダ（`Connection` とそれが名指すもの、`Keep-Alive`、`Te`、`Trailer`、`Transfer-Encoding`、`Upgrade`、`Proxy-*`） | HTTP の規則どおり捨てる | 接続ごとの値であり、転送するものではない |
| `Host` | 上流のホスト名にする | 上流の TLS と仮想ホストのため |

ほかのヘッダ（`Content-Type`、`Accept`、`Accept-Encoding`、`session_id`、`x-client-request-id`、OpenAI の SDK が付ける `OpenAI-*`・`X-Stainless-*` など）はそのまま送る。応答のヘッダは hop-by-hop のもの以外をそのまま返す。

`Accept-Encoding` もそのまま送るので、圧縮された応答は圧縮されたまま呼び手へ届く。Proxy が伸張すると、本文を変えることになり、ストリームの区切りもずれる。

### 通すのは決めたパスとメソッドだけ

既定で通すのは `POST /v1/responses` と `GET /v1/models` の 2 つだけである。完全一致で比べ、`/v1/responses/<id>` のような下のパスは通さない。一覧は設定で変えられる。

- パスが一覧に無ければ 404 を返す。
- パスはあるがメソッドが違えば 405 を返し、`Allow` に許すメソッドを書く。

サブスクリプションの token で何ができるかは OpenAI の側が決めるが、それを広く通す理由はこちらには無い。エージェントがモデルと話すのに要るのは応答の生成と、モデルの一覧くらいである。ファイルのアップロードや、保存した応答の取り出し・削除などは、要るとわかったときに一覧へ足す。

上流の URL は設定で変えられ、既定は `https://api.openai.com/v1` である。要求のパスの `/v1` より後ろを、上流の URL のパスの後ろにつなげる。クエリ文字列はそのまま送る。

### ストリームは届いたそばから流す

応答の本文はバッファせず、上流から読めた分をすぐに呼び手へ書き、flush する。Server-Sent Events の応答では、イベント 1 つが届くたびに呼び手に見えなければならない。要求の本文も同じく、読んだそばから上流へ送る。

時間の制限は、長いターンを切らないように置く。

| 制限 | 値 | 理由 |
|---|---|---|
| 要求のヘッダを読み終えるまで | 10 秒 | 遅いクライアントで接続を塞がれないため |
| 上流が応答のヘッダを返すまで | 既定 10 分、設定で変えられる | 思考の長いモデルは、最初のバイトまでに時間がかかる |
| 応答の本文の全体 | 制限しない | ストリームはターンが終わるまで続く |

呼び手が接続を切れば、上流への要求も取り消す。

### 失敗したときに返すもの

- token がまだ無い（ログイン前）、または期限が切れていて refresh もできない: 503。
- 上流に接続できない、上流が応答のヘッダを返さない: 502。
- 上流が返したエラー（401、429 など）は、本文ごとそのまま返す。Proxy は要求をやり直さない。本文はもう上流へ流してしまっており、残っていない。

Proxy が自分で返すエラーの本文は短い文だけで、token・アサーション・上流のエラーの本文は含めない（ADR 0005）。

### 退けた案

**LiteLLM などの汎用の LLM Proxy を使う。** 既にある部品で済み、Chat Completions への橋渡しも付いてくる。しかし橋渡しは、思考の続きと prompt cache の鍵を落とした。Responses API のまま通すなら、汎用の Proxy が持つ機能のほとんどは使わず、残るのは資格情報の付け替えだけになる。

**本文を読んで直す。** ChatGPT のサインインの token では受け付けられない欄を外す、などである。呼び手の SDK の版によって送る欄が変わるので、Proxy がそれを追いかけることになる。呼び手が正しい形で送れば済むことであり、Proxy はそれを前提にする。

## Consequences

呼び手が送ったものは、資格情報と転送の都合のヘッダを除いて、すべて上流へ届く。思考の続きや prompt cache の鍵が落ちることはない。代わりに、呼び手は ChatGPT のサインインの token で受け付けられる形の要求を、自分で組み立てなければならない。

上流のエラーはそのまま呼び手に見える。429 のような利用量の上限は、同じ token を使う呼び手のすべてで共有される。

通すパスを足すには設定を変える。足し忘れたパスは 404 になり、通ってしまう方向には倒れない。
